## 步兵方案比较

队伍已确认本车枪管装有弹丸通过检测开关，工程通过定时中断运行。当前需求是在下一帧裁判热量到达前，根据本周期已确认通过的数量估计当前热量。算法输入为本周期新增数量、经过时间和冷却速率，允许一拍新增多发。开关的硬件采集与实车验证待接入。

| 热量信息来源 | 可以核对的事实 | 选型前需要确认 |
| --- | --- | --- |
| 裁判回传 | 最近一帧上报的热量 | 步兵车端是否收到该字段，两次更新实际相隔多久 |
| 本地估算 | 枪管开关提供本周期新增数量 | 周期统计是否有重复或遗漏，算法实际调用周期是否稳定 |
| 回传与估算对照 | 同一时段内两条热量记录的差异 | 能否对齐时间，区分报文延迟与估算偏差 |

以裁判回传作为对照基准。若已有步兵日志，优先核查连续报文的接收时间和热量值。比较两条记录时，还需确认它们分别对应哪个时刻。保留裁判热量与上限各自的接收时间。

## 算法层边界与后续优化

模块定位于工程算法层，保持纯 C 和少依赖。现有估算器只依赖标准类型头文件 `stdint.h`、`stdbool.h`，输入和状态均由调用方持有。

- 工程负责开关采集、信号确认、计时、调度及裁判协议解码，将每周期确认后的新增数量及周期时长传给算法。
- 算法根据输入维护热量估值和有效状态，周期时长通过参数传入，参数与具体兵种的对应关系由工程登记。
- 日志、显示和两路热量记录的对照由使用工程接入。当前源码提供独立的估值读取及裁判热量状态判断，自动保存、对齐和差值统计待实现。

当前加热与冷却模型属于基础版本，已改为工程定时周期输入。后续用实测数据检查初始热量、周期内事件分布、冷却规则和裁判数据时间差对误差的影响。每项优化以明确的问题、输入条件及验证结果为依据。

## 周期计数热量估算

[`heat_estimate.h`](heat_estimate.h) 提供一个周期更新的估算器。每个实例负责一个通道。算法依赖 `stdint.h` 和 `stdbool.h`，由调用方持有状态，使用固定内存。赛季参数集中在独立规则头文件，使用方按实际性能类型选取；测试同时覆盖两种规则配置。

1. 用 `heat_estimate_begin(initial_heat, heat_per_event, cooling_period_ms)` 登记开始统计新增量之前的已知热量、每发对应的热量和冷却结算周期。初始化将本地结算相位置零。例如从已确认零热量时开始，提供零热量。中途接入时，起点热量与统计开始的时间需要对应。
2. 每周期调用一次 `heat_estimate_step(estimate, new_events, elapsed_ms, cooling_per_s)`。`new_events` 是自上次调用以来的新增量，可以为零或多发。`elapsed_ms` 是本次区间的毫秒时长，`cooling_per_s` 是本次冷却结算采用的每秒冷却值。每个区间仅交付一次，累计计数的差分在工程侧完成。
3. 用 `heat_estimate_read(estimate, output)` 读取最近一次计算后的估值，单位为千分之一热量。读取不会再扣冷却。若期间没有新增量，定时调用仍须继续，以更新冷却。此接口直接替换原来的逐事件时间戳接口。

每拍先累计经过时间，只有达到配置的冷却结算周期时才扣除完整结算次数对应的冷却量，再把本拍新增量统一计在区间末尾。不足一个结算周期的时间保留到下一拍。时间使用 64 位中间结果，毫秒任务合并调用时也能保留余量。读取操作只返回最近一拍结果。

由同一执行上下文更新和读取估算器。若开关计数由其他中断更新，工程读取累计计数快照，使用同宽度无符号差值计算新增量，再更新上一拍快照。计数自然回绕可按该差值计算，计数器重置需要重建统计起点。采集记录的共享和临界区由工程实现。算法无法识别采集端重复计数，也无法验证新增量是否已被交付过。同一拍需要跨越多个冷却结算点且冷却速率发生变化时，工程按速率生效时刻分别提交区间。

普通裁判报文接收时间无法证明其包含了哪些本地计数。当前估算器由显式起点初始化，裁判数据单独检查。本地初始化时的冷却相位也尚未与裁判时钟对齐，同一拍内新增量和冷却的先后由周期模型约定，估算误差仍需实测核查。

## 裁判回传与验证

`heat_monitor_report` 一次返回两路日志状态。`estimated_status` 将本地估值与有效上限比较，保留千分之一热量的精度。`referee_status` 则基于裁判热量和上限各自的接收时间。调用方应在同一次采样中调用 `heat_estimate_read`，读取成功时传入数值地址，失败时传 `NULL`。有效的零热量与缺失估值有不同状态。若估算任务中断，调用方也应传 `NULL`，接口自身无法检测任务停更。

上限仍有效时，裁判热量过期只影响裁判状态。若上限过期，两路有读数时均返回过期。日志和界面应分别呈现两路状态；例如估值 88.001、上限 88、有效裁判值 87 时，本地显示高于上限，裁判显示低于上限。两路差异仍需结合回传时刻解释。

`heat_monitor_compare` 接受同一机器人、同一热量通道的热量和上限两项已解码读数。输出为数据缺失、数据过期、低于上限、等于上限或高于上限，供日志与显示使用。等于上限描述数值关系，比赛判罚以裁判为准。此版本范围限于只读监测。

调用方为每项读数保存数值、接收标志与接收时间，并根据各自报文的实际周期给出有效期（毫秒）。有效期包含截止时刻。比较使用同一单调毫秒时钟上的一致快照；首帧前、重启及重新建立会话时清除接收标志。快照的实际年龄应小于一个完整的 32 位毫秒计数周期。模块按值接收数据，没有共享可变状态。

在本目录分别编译并运行两个测试程序。

```sh
gcc -std=c99 -Wall -Wextra -Werror -I. heat_monitor.c tests/test_heat_monitor.c -o heat_test
gcc -std=c99 -Wall -Wextra -Werror -I. heat_estimate.c tests/test_heat_estimate.c -o heat_estimate_test
```

回传测试覆盖缺帧、两路独立过期、有效期边界、三种数值关系及计时回绕。周期估算测试覆盖两种规则参数、一拍多发、结算时刻前后、结算余量、冷却到零后计入新增量、冷却增益数值、1 ms 连续调用和合并空闲区间的一致性、重建起点及数值范围。固件构建和实车验证待接入后完成。

### 离线回放：冷却相位对超限预警的影响

主机回放直接编译 `heat_estimate.c`，逐毫秒调用更新和读取接口。参考时间线使用独立的绝对时钟，以十分之一热量记账。每组从相同热量开始，输入完全相同。本地第一次冷却在 100 ms，参考侧先取同相的 100 ms，再将第一次冷却遍历 1 至 99 ms，之后都每隔 100 ms 冷却一次。每次回放 300 ms，增益从指定毫秒起生效，同毫秒内双方均先冷却后计数。

同相时五组的每个采样点均一致。下表列出错相时所有采样点、所有偏移中的最大差值，单位为热量。超限条件取严格大于本组上限。“误报”表示仅本地值超限，“漏报”表示仅参考值超限。这里比较即时数值，未模拟裁判锁定状态。

| 模拟输入 | 最大高估 | 最大低估 | 出现误报 | 出现漏报 |
| --- | ---: | ---: | --- | --- |
| 冷却优先，从上限开始，全程无新增 | 2.4 | 0 | 否 | 否 |
| 爆发优先，从上限减 9 开始，第 99、100、101 ms 各新增一次 | 1.4 | 0 | 是 | 否 |
| 冷却优先，同上组相对起点和计数记录 | 2.4 | 0 | 是 | 否 |
| 冷却优先，从零开始，仅第 99 ms 新增一次 | 0 | 2.4 | 否 | 否 |
| 冷却优先，从上限加 3 开始，无新增，第 75 ms 起冷却速率变为 1.5 倍 | 3.6 | 1.2 | 是 | 是 |

例如在最后一组，取参考侧首次结算为 50 ms。参考值从 91 降至 88.6，本地到 100 ms 才首次结算，此时增益已生效，本地值降至 87.4。同一时刻两者分处上限 88 的两侧。即使计数完全一致，冷却时刻也足以改变一次预警判断。这些误差极值只覆盖表中的输入、整数毫秒偏移和同刻顺序约定。实际裁判结算相位、采集误差与报文延迟仍需实测。

复现时，在本目录执行 `gcc -std=c99 -O2 -Wall -Wextra -Werror -I. heat_estimate.c tests/replay_heat_phase.c -o heat_phase`，再运行生成的程序。每行依次输出场景名、最大高估和低估（千分之一热量）、是否误报和漏报（1 表示出现）。
